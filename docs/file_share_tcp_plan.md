# File sharing over a TCP connection of its own (plan)

Branch `custom_campaigns`, 2026-11-15. Not built. Follows
[map_transfer_plan.md](map_transfer_plan.md), whose MCC and CE paths stay as
they are for OpenCE machines.

## Goal

Between two SlipstreamCE machines, map and package files go over a TCP
connection used for nothing else, encrypted as the tunnel is, and as fast as
the line allows:

- **Outside a game** (menus, lobby, a dedicated server between rounds): 100%
  of the line's top speed.
- **In a game**: the top speed less the game's traffic at the moment, less 5%
  of the top speed: `budget = 0.95 * C - G`, never below 0 (a transfer pauses,
  its connection kept, while the game takes it all).

`C` is the top speed of the line in the direction that limits the transfer
(the sender's upload, the receiver's download): what is measured, but never
more than the machine's upload limit (`network.map_share_upload` hosting,
`network.map_seed_upload` otherwise), which now goes up to 250 MB/s (256000
KB/s). The limit is the most a connection may send even outside a game. `G` is
this machine's own game traffic in that direction right now.

Decided 2026-11-15: the ciphers are measured on the Z Fold alone; the Switch
opens 4 connections to a source; about 40 MB/s is plenty.

## Why a new connection

- MCC files ride the game's reliable connection in 3 KB chunks, 32 requests
  in flight (OpenCE's protocol, network version 44): about 96 KB a round trip
  however fast the line is, and served in the game's frame.
- Over the internet that connection is a KCP stream in the tunnel with the
  game's fixed 128-message window; its ChaCha20-Poly1305 is portable C, in the
  guest.
- The system's TCP finds and fills a line by itself, with large buffers and
  no timer of ours, and the host's native threads can use the CPU's AES
  instructions. What it lacks is the tunnel's encryption and its way through
  NATs: both are planned below, with the tunnel kept as the fallback.

## Hardware-accelerated encryption

ChaCha20-Poly1305 has no instructions of its own; it is sped up only with
vector code (NEON, SSSE3/AVX2). AES-GCM has instructions on every target
CPU:

| Platform | CPU | AES-GCM instructions |
|---|---|---|
| Switch | Cortex-A57 (Tegra X1) | ARMv8 Crypto Extensions: AESE/AESMC, PMULL (libnx's own AES uses them) |
| Android | ARMv8 phones | the same, nearly all; checked at run time (`getauxval(AT_HWCAP)`: `HWCAP_AES`, `HWCAP_PMULL`) |
| PS5 | Zen 2 | AES-NI and PCLMULQDQ (CPUID) |

Libraries that use them:

- **libsodium** (ISC, C): AES-256-GCM with AES-NI/PCLMUL, and with ARM
  Crypto Extensions since 1.0.19; ChaCha20 with SSSE3/AVX2 on x86 only
  (portable on ARM). Its run-time CPU check reads `getauxval` on Linux and
  Android; on the Switch (Horizon) it would need a line of ours (the A57
  always has them) and on the PS5 CPUID works.
- **mbedTLS 3.6** (Apache-2.0): AES and GCM with AES-NI/PCLMUL and with
  ARMv8 (`MBEDTLS_AESCE_C`); ChaCha20 portable. devkitPro packages it for the
  Switch.
- **BoringSSL / OpenSSL**: the fastest (hand-written assembly for AES-GCM and
  for ChaCha20 with NEON and AVX2), but large, and their assembly is
  generated by Perl scripts per toolchain: not worth three toolchains.
- **Our own**, as `host_mcc_hash.c` does SHA-256 and CRC32: AES-256-GCM in
  about 400 lines with intrinsics (`vaeseq_u8`/`vmull_p64` under
  `__attribute__((target("+aes")))`, `_mm_aesenc_si128`/`_mm_clmulepi64_si128`
  under `target("aes,pclmul")`), chosen at run time, checked against NIST's
  vectors and against Python's `cryptography` in a test.

**Recommendation**: AES-256-GCM as the cipher whenever both ends have the
instructions (every device we test on), ChaCha20-Poly1305 (the tunnel's code,
moved to the host) otherwise. Take libsodium's two AEADs (only their source
files, compiled into the host as `host_mcc_hash.c` is, with the Switch's
check patched), or write the AES-GCM ourselves on `host_mcc_hash.c`'s
pattern if a library on three toolchains turns out heavier than the code.
X25519 and HMAC-SHA256 stay ours (Monocypher, `p2p_crypto.c`), moved or
duplicated into the host.

Step 0 measures before deciding: each cipher's MB/s on the Z Fold, one
thread (the portable ChaCha20 we have now included). The target is about 40
MB/s; the instructions matter at that speed on the Switch's 1 GHz A57s, which
also run the game, and hardly over most internet uploads.

### Measured on the Z Fold (2026-11-15)

64 KB records, one thread, sealed in a loop for 2 seconds; the outputs were
first checked against Python's `cryptography` (byte for byte, 1000 bytes with
additional data). The AES-256-GCM is code written for the measurement (the
instructions directly: AESE/AESMC, PMULL for GHASH, four blocks at a time).

| Core | AES-256-GCM (instructions) | ChaCha20-Poly1305 (p2p_crypto.c) | XChaCha20-Poly1305 (Monocypher) |
|---|---|---|---|
| any (scheduler's) | 2015 MB/s | 227 MB/s | 230 MB/s |
| a little core (cpu 0) | 954 MB/s | 261 MB/s | 237 MB/s |
| the big core (cpu 7) | 2631 MB/s | 307 MB/s | 391 MB/s |

AES with the instructions is 4 to 9 times as fast as either ChaCha20. At 40
MB/s it costs a little core about 4% of its time, ChaCha20 about 15%; the
Switch's A57s at 1 GHz are slower than the Z Fold's little cores, so there the
difference is between a few percent and a good part of a core the game needs.

**Decided**: AES-256-GCM with the instructions, our own (the measurement's
code grown into `host_file_share_crypto.c` on `host_mcc_hash.c`'s pattern:
the instructions under `target` attributes, checked at run time, with
NIST's vectors and Python's `cryptography` in a test); ChaCha20-Poly1305 (the
tunnel's code) where a CPU lacks them. No library to build on three
toolchains.

## Where it runs

In the **host**, as the heavy MCC work already is (`host_mcc_hash.c`,
`steam_downloads.c`; the guest image has little room left): one native
thread per machine for every file connection, in a new
`port/android/host/host_file_share.c`, compiled for Android, the Switch and
the PS5 as `host_mcc_hash.c` is. It owns the sockets, the handshake, the
encryption, reading the served files and writing the received ones
(`.part`, then renamed), and the SHA-256 checks (the host's, with the CPU's
instructions).

The **guest** decides what moves and between whom, as now: imports such as
`host_file_share_serve/_fetch/_status/_cancel/_facts`, and an adapter in
`port/linux/game/file_share.c` used by `mcc_share.c` (and later
`map_share.c`).

## Negotiation

- A capability `file_share_tcp`, version 1, in `network_extensions.c`'s
  table. The host uses the new path with a machine only when
  `network_extension_agreed(machine, "file_share_tcp", 1)`; a client only
  when `network_extension_host_has("file_share_tcp", 1)`. An OpenCE machine
  sees nothing and keeps today's protocol.
- The MCC offer (files, sizes, SHA-256, fingerprint) and admission stay on
  the game's connection, unchanged. The joiner fetches the files over the
  new connection and tells the host's MCC session it has each one with
  `MCC_SHARE_OP_HAVE`, as Part A of map_transfer_plan.md does for a file
  from the Workshop (`reuse_file` / `reuse_wait`). The host's state machine,
  its `DONE(1)` and the fingerprint check at the end do not change. If the new
  connection cannot be made within a few seconds, or fails, the file is asked
  of the host the old way.
- The host gives the joiner, in an extension message over the game's
  connection: a random 32-byte token for this machine and game, the host's
  addresses for the file port (LAN, public with the UPnP port), and the
  piece hashes of each file (256 KB pieces, from the host's SHA-256). A
  token is good for one machine, one game, and is forgotten when the machine
  leaves.

## Reaching the other machine

A new port, `FILE_SHARE_PORT` (5154). The joiner tries, in order, stopping
at the first that answers the handshake:

1. **LAN**: the host's LAN address when it is in the joiner's subnet (a LAN
   game's addresses are those already).
2. **Direct to the host**: the host's public address (STUN's, which p2p.c
   has) at its forwarded TCP port, a 2-second timeout. `posix_upnp.c` asks
   the router for a TCP forwarding of 5154 alongside the tunnel's UDP one,
   with the same lease, renewal, clean-up of stale ones and "no router
   behind a private address" rule.
3. **Reversed**: when the joiner has a forwarded port and the host does not,
   the joiner says so and the host connects to it (which way the connection
   was made does not change which way the files go).
4. **Through the tunnel**: the joiner's host thread connects to the p2p
   stand-in for the host's virtual address and port 5154 (p2p.c makes a
   local TCP listener per peer and port; the guest tells the host thread its
   local port). The stream is a KCP one; 5154 joins 5153 in getting the
   map-sharing window (`stream_make_bulk`). Slower, but it reaches everyone
   the game reaches. (Later, perhaps: no record encryption on this path,
   since the tunnel already seals it; at first, one code path.)

A machine behind a carrier's NAT (most phones on mobile data) gets 4 only;
the host of a server usually 1 or 2.

## The handshake

Over the new TCP connection, before anything else:

1. Joiner -> host: magic `SLFS`, version 1, an ephemeral X25519 public key,
   a 32-byte nonce, the token's id (8 bytes, not the token), and the ciphers
   it can do quickly, fastest first (AES-256-GCM only if it has the
   instructions).
2. Host -> joiner: its ephemeral X25519 public key, its nonce, the cipher
   chosen (the first of the joiner's list the host also does quickly, else
   ChaCha20-Poly1305).
3. Both: `secret = X25519(own, other)`; keys = HKDF-SHA256 with the two
   nonces as salt and `secret || token` as input, labels "slfs joiner" and
   "slfs host": one key for each direction, as the tunnel's.
4. Both send, as their first record, an HMAC-SHA256 of the whole handshake
   with their key: each proves it holds the token and the same secret. A
   wrong one closes the connection; a source address that fails a few
   times is ignored for a while.

The token arrives inside the tunnel's encryption over the internet (the game's
connection is in the tunnel), so a stranger who finds the forwarded port
cannot complete a handshake; the ephemeral keys give each connection keys of
its own (forward secrecy). On a LAN the game's connection is plain TCP, as it
is for the game itself; someone on the LAN who reads it could take the token.
That is the LAN's usual trust, the same as the game's.

## The records

- Each record: a 3-byte length, then the ciphertext and its 16-byte tag. The
  length is the AEAD's additional data. The nonce is a 96-bit counter per
  direction; a connection is closed long before it could wrap.
- Up to 64 KB of plaintext a record: fewer tags and system calls a second
  than the tunnel's 1.2 KB packets.
- Inside, frames:
  - `HAVE` (which files and pieces this end has),
  - `WANT` (a file and a range, as large as the joiner likes: a whole file),
  - `DATA` (file, offset, bytes),
  - `ACK` (bytes received so far, the sender's timestamp echoed, and the
    receiver's rate limit for this sender, below),
  - `CANCEL`, `BYE`.
- No request window: the joiner asks for whole files or large ranges and
  TCP's flow control does the rest. Each 256 KB piece is checked against its
  hash as it completes; a bad piece is asked again, a source that sends two
  is dropped.

## Measuring the top speed (C) and the game (G)

The receiver sends an `ACK` every 64 KB or 25 ms. From the bytes it says it
has and the timestamps it echoes, the sender gets the **delivery rate** and
the **round trip** on every platform. That avoids depending on `TCP_INFO`,
which Android has (with `tcpi_min_rtt` and `tcpi_delivery_rate`) but the
Switch and the PS5 may not.

- **`C_up`** (a sender's upload): the largest delivery rate of all its file
  connections together over the last 10 seconds while they were not held back
  (BBR's max filter), never above the upload limit. Kept on the card per public address (the host's line
  rarely changes), so a host that served a transfer before starts from it.
- **`C_down`** (a receiver's download): the same, from what it receives.
- **The lowest round trip** seen on each connection, for the delay check
  below.
- **`G`**: the game's own bytes a second in each direction, counted by the
  guest where they leave and arrive (`xnet.c` for a LAN game's sockets, `p2p.c`
  for the tunnel's datagrams and the game's KCP streams), in 100 ms buckets;
  `G` is the largest of the last five (so it reacts to a burst within 100 ms
  and lets go after half a second). Passed to the host thread with the other
  facts (`host_file_share_facts`) every 100 ms.

## The rate

**Outside a game**: the sender writes as fast as the socket takes it, up to
the upload limit (250 MB/s at most), with large buffers
(`SO_SNDBUF`/`SO_RCVBUF` of a few MB where the system allows); the system's TCP
fills the line. That is also when `C` is learned best.

**In a game**: each machine paces its sending with a token bucket.

- A sender's total: `0.95 * C_up - G_up`, shared among its connections by
  what each still has to send.
- A receiver's total: `0.95 * C_down - G_down`, shared among its sources; it
  tells each its share in its `ACK`s, and a sender never exceeds what the
  receiver allows.
- **Keeping `C` honest while capped**: if a connection's round trip rises
  more than 30 ms above its lowest while it sends at its rate (a queue is
  building: `C` was too high, or something else shares the line), `C` drops
  10% at once; if the round trip stays flat and the connection keeps up with
  its rate, `C` rises 2% a round trip, up to the last uncapped measurement.
- **No measurement yet** (a joiner joining a game in progress, a host that
  never served): it starts at 1 MB/s and grows 25% a round trip while the
  round trip stays flat, stopping at the first rise. That is slower than
  outside a game, so the game is never flooded to find out.
- A budget at or below 0 pauses sending (`ACK`s go on), and sending picks up
  when it is above again.

## Platform limits to raise

- **Switch**: libnx's socket buffers are capped at 512 KB
  (`tcp_tx_buf_max_size` / `tcp_rx_buf_max_size`, `host_main.c`), so one
  connection carries at most 512 KB a round trip: about 10 MB/s at 50 ms,
  3.4 MB/s at 150 ms. The Switch opens **4 connections** to a source, each
  carrying its own files or ranges (about 2 MB a round trip together); raising
  the buffers is left unless 4 fall short of about 40 MB/s.
- **All**: the record size, the read size from the card (1 to 4 MB at a
  time on a thread of its own, as `host_mcc_hash.c` reads), and writes in
  large blocks, so the card is not what limits.

## Stages

0. **Measured** on the Z Fold (above): AES-256-GCM with the instructions, our
   own. Done with stage
   0: the upload limits' top raised to 250 MB/s (both screens, the server's
   command, the config's help).
1. **The connection on a LAN**: `host_file_share.c` (handshake, records,
   frames, rates unlimited), the capability, and MCC files fetched with it
   and reported with `HAVE`; the old path when it fails. Test between two
   phones on the LAN: the transfer near the Wi-Fi's speed.

   **Built 2026-11-15** (awaiting the device test, the Switch and a phone), as
   follows where it differs from the above:
   - It replaces `mcc_fast.c` (commit f1ce8261a, 2026-11-14: the same port,
     plain, in the guest), whose session hooks it keeps
     (`transfer_elsewhere`).
   - The joiner's host thread writes each file to the `.part` its stage names
     (`mcc_share_stage_external_path`), hashes it as it comes (the CPU's
     SHA-256), and the stage takes it whole (`mcc_share_stage_external_done`):
     the guest neither reads nor hashes the files. No `HAVE`: the host's
     transfer counts the connection's bytes as its progress and is marked
     fully asked for once every file was sent, then the joiner's `DONE(1)` and
     the fingerprint check as before.
   - No address check: the token is the joiner's proof. The host sends a
     `READY` record first, and the joiner writes nothing before it opens, so a
     wrong token fails before any file is touched (the host's chunks then).
   - Over the internet the joiner's host thread connects to p2p.c's stand-in
     for the host (`p2p_outgoing`), so the tunnel carries it with map
     sharing's KCP settings, as it did `mcc_fast`'s; the host's p2p.c takes the
     stream while the host's listener is up (`p2p_set_file_share_listening`).
     That is stage 3's fallback, already there.
   - The rate is the upload limit times `network.map_upload_in_game` in a
     game, as before (stage 2 replaces it).
   - Tests: `tools/test_host_file_share.py` (the ciphers against Python's
     `cryptography`; a host and a joiner over loopback: every byte, the rate,
     a wrong token, an unknown session, a bad hash, stopping),
     `tools/test_mcc_share.py`'s `external_file*`,
     `tools/test_network_extensions.py`'s data message. The ARM AES-GCM was
     checked on the Z Fold against Python too.
   - The log says what happened: `file share: receiving session ... (ARMv8 AES
     and PMULL)`, `file share: received N MB in S s (R MB/s)` on the joiner,
     `sent ...` on the host, and `mcc share: ... over the host's file
     connection` or why it fell back to the chunks.
   **Custom Edition maps, built 2026-11-15** (the user chose the host as one of
   the swarm's sources, over the host alone or the whole swarm on 5154):
   - When the host offers its files (`host_offer`) to a machine with
     `file_share_tcp`, it gives them to its file connection under a session of
     its own (high bit set) and sends the token, marked for a Custom Edition
     map (the data's 37th byte: 0 MCC, 1 CE).
   - The joiner's connections' thread (`fs_source_update`) opens the host's
     file connection in pieces mode (`host_fs_pieces_*`) and asks it up to 32
     pieces at once, those no one was asked for, in order; its host thread
     takes each in, checks it against its BLAKE2b hash, and the connections'
     thread writes it as any other piece (`download_piece_had`): the `.part`
     has one writer. Other players' connections go on; the host's own 5153
     connection gives only the pieces' hashes while the file connection goes.
   - A piece that does not match, or the connection lost, ends the file
     connection for the download and gives what it was asked back to the
     swarm.
   - One listener serves both (`mcc_share.c` opens it for MCC or CE hosting).
   - Tests: `tools/test_host_file_share.py`'s `test_pieces`; the map sharing
     harness tests know the new structure.
2. **The rate**: the `ACK`s, `C` and `G`, the in-game budget, the delay check.

   **Built 2026-11-15, with stage 3**, as follows where it differs:
   - No `ACK`s: `C` comes from the sender's own sends, in half seconds; one in
     which sends waited on the socket a tenth of it or more was the line, full
     (the socket buffer backs up only when the line does); `C` is the most of
     those in the last ten seconds.
   - The delay check is the game's own: the host's round trips to its clients
     (`network_distributed_host_round_trip_milliseconds`), not the file
     connection's. 30 ms above the least of the last minute while files go
     out: `C` down a tenth; else up 2% a half second while the allowance is
     used (25% while no full line has measured it, from 1 MB/s).
   - `G` is the game's datagrams (`xnet.c`'s `sendto`, 28 bytes a datagram for
     the headers), the most of the last half second's tenths.
   - Only the host's (sender's) side; a receiver's downlink is not budgeted.
   - The allowance (`host_fs_allowance`) replaces `map_upload_in_game` for the
     swarm (5153) and OpenCE's MCC chunks too, each still under its limit.
   - In a game where the game takes the whole line: 16 KB/s, so the connection
     pauses rather than times out.
   - The host logs `file share: rate …` every 5 s while it serves.
   - Tests: `tools/test_host_file_share.py`'s `test_rate_*`.
   Test: a hosted server with players in a game while a joiner downloads; the
   players' ping must not rise by more than a few ms.
3. **The internet**: UPnP's TCP forwarding, the direct attempt, the reversed
   connection, the tunnel fallback. Test from a phone on mobile data (the
   fallback) and from another house (direct).
   **Stage 3 built 2026-11-15**: `posix_upnp_forward_tcp`; p2p.c's UPnP
   thread forwards 5154 while the host's file connection listens in an
   internet game (renewed with the UDP one, removed at its end and at exit);
   the token message carries the forwarded address and port (bytes 37 to 42);
   a joiner of a host over the tunnel tries it first (3 s to connect, 4 s for
   the reply), then the tunnel's stand-in. Not built: the reversed
   connection. Tests: `test_direct_first`, `test_direct_falls_back`.
4. **The Switch's 4 connections** a source; its buffers only if they fall
   short of about 40 MB/s.

   **Built 2026-11-15, for every platform** (one internet joiner: 3.2 MB/s
   over one connection on a 265 Mbit/s upload and a 322 Mbit/s download; CUBIC
   halves a connection's window at each loss): a joiner opens 16 connections
   to the host (4 on the Switch), all through the one port; the first proves
   the token, the others open after it. A map's pieces are shared between
   them; an MCC package's files go in 1 MB ranges, put back in order in memory
   and written and hashed in order (one writer, the hash as it comes). A
   connection that drops gives its piece or range back. The host takes 32
   connections at once, 16 a transfer, one allowance for all. BBR is asked
   for where the sender's kernel allows it (the S21 FE's, not the Z Fold's);
   socket buffers fall back from 4 MB until the system takes one (a BSD
   stack refuses a size past its limit and keeps its small default).
5. **Later**: CE maps (`map_share.c`) over the same connection between
   SlipstreamCE machines; other players as sources (the host hands out a
   token for each pair, as it does the sources' list now); no record
   encryption inside the tunnel; IPv6 addresses for a direct connection
   where carriers allow it.

Each stage: its own commit, Android/Switch/PS5 builds, the harness compared
with main, and a device test as above.

## Open questions

- Is the Switch's and the PS5's round trip available from their TCP stacks
  (`TCP_INFO`)? The plan does not need it (the `ACK`s give it), but it would
  be a check.
- On a dedicated server with many joiners at once, is the fair share among
  connections enough, or should a joiner who is in the lobby (not yet
  playing) get priority over one already in the game?
